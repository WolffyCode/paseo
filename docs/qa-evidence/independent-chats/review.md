## 审查结论

### 代码逻辑完整性

创建入口、源类型验证、运行目录分配、首次消息、持久化、目录广播、客户端
归一化、冷缓存、导航和关闭/归档分别由已有的对应模块负责。复用创建操作的
幂等身份与现有 Agent 生命周期。目录由 daemon 生成，客户端不能用 chat source
指定任意路径；首个 Agent 的 cwd 使用分配目录。已知失败与未知结果分别处理。

### 业务自洽性

用户管理的是独立聊天，内部执行 backing 不进入项目选择和项目侧栏。关闭视图
与归档是两个不同动作。普通项目名叫 Chats 或路径末尾叫 chat 仍然是普通项目。
历史聊天保留原来的 provider/session；本期没有宣称跨提供商迁移会话。

### 需求合理性与完整性

使用前提是连接已有 host，并有可用的 coding-agent provider。用户无需 Git 或
项目即可讨论和进行临时任务。实现完整的创建、继续、保存、重命名、归档及失败
恢复流程。未引入多模型群聊、全局语音、角色配置或整体视觉重做。

### 代码质量

输入和 wire schema 保持类型约束；新增 metadata 用显式 purpose，未使用名称、
路径推断或兼容映射。缓存和持久化保留同一字段。样式使用现有主题与 UI primitive，
操作状态使用 reducer，复杂度检查通过后才提交。继续使用已有 CI/test suites，
没有增加 feature-specific npm 脚本。没有修改版本、发布配置或重启 6767 daemon。

## 发现的问题与优化修复

| 问题                                                                    | 在原处修复                                                            | 验证方式                                          |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------- |
| 缓存序列化遗漏聊天 purpose，冷读可能混入项目                            | 补齐 workspace/project 缓存 schema 和序列化字段                       | ReplicaCache 冷读回归                             |
| Agent 启动失败留下活动的空白聊天                                        | 在初始 Agent 创建失败发布前归档未完成分配；重试可恢复同一 allocation  | 失败前红测、修复后同 key 重试绿测                 |
| mkdir 已知失败被通用创建框架标成未知结果，重试被阻止                    | 目录分配边界抛出 typed error，创建所有者归为注册前拒绝                | 真实文件系统阻塞、恢复后浏览器重试                |
| 私有聊天目录被“新建工作区”当成默认项目                                  | 在项目上下文解析和入口中排除 chat purpose                             | 业务断言与浏览器 URL/普通项目回归                 |
| 关闭 root Agent 标签页会归档，导致聊天无法从列表继续                    | 在关闭策略所有者加入 chat 的 layout-only 语义，批量关闭也使用同一策略 | 策略 suite 与浏览器关闭/重开/历史消息验证         |
| SDK 对支持 creation lifecycle、但不支持 chats 的主机仍可能发送新 source | 在 SDK 创建边界检查实际 capability                                    | 两种旧主机能力组合均在请求前拒绝                  |
| 后台完成的创建可能清空用户后来编辑的草稿                                | 成功后仅清除仍与提交快照相同的内容                                    | 正常提交/失败草稿流程；新版草稿保护是内容比较策略 |

## 合并方案

1. 确认 develop 的基线是否变化；变化时将新的 develop 合入开发分支，检查冲突。
2. 保留本功能的实现、回归和文档提交，不带入旧 PR 的版本、发布或无关变更。
3. 使用既有 CI 进行跨平台检查；原生设备和真实 provider 按上表补验，不将本地
   Chromium 结果描述成已验证全部平台。
4. 本地集成采用正常合并：

```bash
git switch develop
git merge --no-ff codex/independent-chats
npm run build:server
npm run typecheck
npm run lint
npm run test:e2e --workspace=@getpaseo/app -- new-workspace.spec.ts --grep 'independent chat|global new workspace uses the last active project' --max-failures=1
```

5. 提交前运行 `npm run format`。合并后确认 chat source、普通工作区、缓存字段、
   capability 与目的字段均在最终 diff 中。回退使用对应合并提交的 `git revert -m 1`，
   不删除聊天目录、用户文件或运行中 Agent 的状态。

## 补充验收与修复测试方案

| 项目          | 操作与通过标准                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| 真 provider   | 在隔离 home 选择已配置 provider，发首条、续聊、停止、关闭重开；ID 和历史保持，原生错误可见                 |
| 移动端        | 真机新建、键盘/附件、滚动列表、重命名 sheet、归档确认、断网重连；控件可点击且无横向溢出                    |
| 桌面 Electron | 隔离用户目录启动，共用功能流程；确认窗口快捷键、模型浮层、系统确认和返回导航                               |
| 多 host       | 两主机各建同名聊天；切 host 不串历史、草稿或目录，断开一个不影响另一个                                     |
| 断线创建      | 分别在分配前、Agent 注册后、首次消息后断线；按同一 operation 查询恢复，不重复创建或发送                    |
| 存储失败      | 目录创建、注册写入、rename、archive 分别注入可定位错误；保留可重试状态和数据，不静默成功                   |
| 旧版本        | 新客户端连接无 chat capability 的 host，显示更新提示且无 create RPC；旧客户端连接新 daemon，普通功能可解析 |
| 普通功能回归  | 项目添加、本地/worktree 创建、子 Agent 关闭、归档/恢复保持原语义                                           |

遇到失败先在 owning suite 加可复现断言，再改对应所有者，跑同一测试文件、
类型、lint 和受影响的用户流程。阻塞级别的问题必须修复并补证据后再合并。
